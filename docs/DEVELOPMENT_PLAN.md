# FoxDroid 开发规划

> 状态：执行中  
> 版本：0.1  
> 日期：2026-09-27  
> 依据：[产品需求文档](./PRD.md) 0.4、[技术路线](./TECHNICAL_ROUTE.md) 0.4

当前完成状态、已知技术债和下一迭代建议见 [项目状态与后续规划](./PROJECT_STATUS.md)。
Android 手机端的分阶段实施任务与退出标准见 [Android 手机端开发规划](./ANDROID_DEVELOPMENT_PLAN.md)。

## 1. 当前开发主轴

当前主轴只有三个组成部分：

1. **Android 手机端**：本地曲库、可选内容服务、四轨触控、低延迟音频与本地判定。
2. **Web 端**：由内容服务直接托管，支持桌面浏览器选歌、键盘游玩和本地判定。
3. **家庭内容服务**：在 NAS/Docker 中扫描和解析曲库，通过版本化接口向 Web 与 Android 客户端提供清单和资源。

Android TV、遥控器导航、USB 跳舞毯、双人、公网服务、云账户和完整 OutFox 兼容均不属于当前 MVP 主轴。

## 2. 规划原则

- 先完成一条能真正游玩的纵向链路，再扩展格式、页面和设备。
- 服务端、Web 和 Android 使用同一份接口定义、内容模型和谱面测试数据。
- 服务端负责内容，客户端负责实时运行；任何网络调用都不得进入判定链路。
- Android 本地模式不得因为服务端功能尚未完成而不可用。
- 每一个新增谱面特性必须同时包含解析样例、时间轴测试和判定测试。
- 每一个新增平台能力必须有真实设备或浏览器验证，不能只凭模拟器判断完成。
- 不为了假设中的未来扩展提前引入微服务、云账户、插件系统或复杂抽象。

## 3. 需求准入与否决机制

后续提出的新需求先经过以下判断，不直接进入开发队列：

| 判断项 | 问题 |
|---|---|
| 主轴关联 | 是否直接改善 Android 手机、桌面 Web 或内容服务的核心体验？ |
| MVP 必要性 | 缺少它是否无法完成“导入/同步—选歌—游玩—结算”闭环？ |
| 复用价值 | 是否同时服务两个客户端，或建立明确的共享基础？ |
| 隔离能力 | 是否能通过独立模块或功能开关实现，而不污染核心判定？ |
| 持续成本 | 是否引入新的平台、协议、账户体系、版权或长期兼容负担？ |
| 里程碑影响 | 是否会推迟当前里程碑，或者迫使已验证部分返工？ |

评审结论只有四种：

- **现在接受**：与主轴直接相关，属于当前 P0，并有明确验收标准。
- **排入后续**：有价值但不阻塞 MVP，记录到候选池，不进入当前迭代。
- **限时验证**：价值或风险未知，允许最多 1–2 个工作日的隔离实验；实验不得改变正式架构。
- **明确拒绝**：偏离目标、收益不足以覆盖复杂度，或与既有约束冲突。

默认规则：新想法不必然进入当前迭代。提出者需要说明它解决的用户问题；只有实现设想、没有用户问题的需求，默认延后。

### 3.1 应主动否定的需求类型

- 在手机/Web MVP 稳定前提前启动 Android TV 专项开发。
- 为了兼容某个罕见歌曲包而一次性引入整个新游戏模式。
- 让服务端参与客户端实时判定、逐帧同步或输入处理。
- 在家庭局域网版本稳定前增加公网暴露、社交、账户或商业支付。
- 为未经验证的规模引入 Kubernetes、消息队列、分布式数据库或多服务拆分。
- 在没有明确许可证前复制闭源客户端、OutFox 专有代码、主题或素材。
- 通过降低判定正确性来换取表面上的格式兼容数量。

### 3.2 可以接受的偏航

以下情况可以暂时偏离计划：

- 发现会否定项目可行性的音频、输入或浏览器限制。
- 发现数据格式或许可证问题会迫使整体路线改变。
- 当前实现出现数据损坏、安全漏洞或不可恢复的兼容问题。
- 一个短期实验能用很低成本消除高风险技术假设。

## 4. 工作流划分

### 4.1 共享规范与测试

- 内容模型与 API 版本。
- `.sm/.ssc` 兼容范围。
- 谱面、时间轴和判定黄金测试数据。
- 资源标识、校验、缓存和错误模型。
- 第三方依赖与许可证清单。

### 4.2 内容服务

- Docker 运行和持久化。
- 曲库扫描、解析、增量更新和错误隔离。
- SQLite 索引。
- 清单、谱面、资源和健康接口。
- Web 静态资源托管。

### 4.3 Web 客户端

- 曲库浏览和选歌。
- 资源准备。
- Web Audio 时钟。
- 键盘输入、渲染、判定和结算。
- 浏览器缓存、失焦暂停和能力诊断。

### 4.4 Android 手机客户端

- 本地歌曲导入和索引。
- 设置页可选内容服务器。
- 清单同步和资源缓存。
- Oboe/AAudio、触控输入、渲染和判定。
- 生命周期、校准和本地成绩。

### 4.5 发布与质量

- 自动构建和测试。
- Docker amd64/arm64 镜像。
- Android 包、隐私和权限检查。
- Web 浏览器矩阵和性能测试。
- 文档、诊断和升级回滚。

## 5. 里程碑

采用双周迭代。下面的时间是工作量级别，不是发布日期承诺；实际日历取决于开发人数和设备到位情况。

手机端与 Web 端具有相同的产品优先级。里程碑先写 Web 纵向切片，是因为它能与服务端在同一部署中最快验证完整链路，并不表示手机端降级；若有两名及以上开发者，M1 的 Web 工作与 M2 的 Android 音频、本地导入和触控基础可以并行推进。单人开发时按 M1、M2 顺序执行，以减少同时维护未稳定接口的返工。

### M0：项目骨架与契约冻结

预计：1 个迭代。

交付：

- 建立服务端、Web、Android 和共享规范的代码目录。
- 确定第一版 API、内容 ID、错误结构和版本策略。
- 建立无版权风险的最小测试歌曲集。
- 建立 `.sm/.ssc` 第一阶段兼容清单。
- 建立基础自动测试和构建检查。

退出标准：

- 同一首测试歌曲可以被规范化为确定、可重复的内容模型。
- Web 与 Android 可以从生成的接口定义构造客户端模型。
- 所有第三方核心依赖有明确许可证记录。

### M1：服务端与 Web 纵向切片

预计：2 个迭代。

交付：

- Docker 服务扫描一份小型 `.sm` 曲库并写入 SQLite。
- 服务根地址提供 Web 客户端。
- Web 完成清单、选歌、资源准备、单首歌曲键盘游玩和结算。
- Web Audio 时钟、基础偏移与失焦暂停可用。
- 损坏歌曲不会阻塞整个曲库。

退出标准：

- 从空数据库到浏览器完成一局游戏可以重复执行。
- 游戏过程中停止服务端不会改变已准备歌曲的判定结果。
- Chrome、Edge、Firefox 当前桌面版至少完成基础验证。

### M2：Android 手机纵向切片

预计：2–3 个迭代。

交付：

- 本地导入一份歌曲包并完成触控游玩。
- 设置页默认关闭内容服务器。
- 打开服务端、填写地址、测试连接、同步清单并游玩远程来源歌曲。
- Oboe/AAudio 时钟、四点触控、基础校准和本地成绩可用。
- 服务端离线不阻塞本地模式。

退出标准：

- 一台 60 Hz 手机和一台高刷新率手机完成端到端验证。
- 网络断开不影响已开始的歌曲。
- 后台切换、音频焦点变化和恢复不会产生错误判定或继续播放失控。

### M3：谱面兼容与共享行为收敛

预计：2–3 个迭代。

交付：

- 完成 MVP 定义内的 `.sm` 和标准 `.ssc` 支持。
- 完成 Tap、Jump、Hold、Roll、Mine、BPM、Offset、Stop、Delay、Warp。
- Web 与 Android 对同一谱面和输入序列得到等价判定结果。
- 完成内容增量、删除、缓存失效和解析器升级处理。
- 完成真实规模曲库扫描和清单同步测试。

退出标准：

- 黄金测试集全部通过。
- 单个损坏文件不会导致清单同步或客户端启动失败。
- 内容模型和 API 达到 `v1` 候选状态，非破坏性问题不再修改字段语义。

### M4：MVP 稳定与发行候选

预计：2 个迭代。

交付：

- 完成加载速度、内存、掉帧、音频 underrun 和缓存容量优化。
- 完成 Android 权限、局域网拒绝和服务器离线体验。
- 完成服务端路径、认证信息、Range 请求和异常输入安全检查。
- 完成 Docker 部署、升级、备份和重建说明。
- 完成 Android 手机和桌面 Web 的发布检查。

退出标准：

- PRD 中手机、Web、服务端的 MVP 验收标准全部满足。
- 已知高严重度缺陷为零。
- TV 需求未被混入 MVP 发布阻塞项。

### M5：MVP 后增强

候选内容：

- Web Gamepad API 与桌面 USB 舞毯。
- PWA、离线策略和显式歌曲下载。
- 背景视频与更多媒体格式。
- 内容服务自动发现和管理页面。
- 更多筛选、统计和成绩同步。

这些项目需要逐项重新经过需求准入，不因出现在候选列表中自动获得开发承诺。

### M6：Android TV 与跳舞毯

只有满足 TV 启动门槛后才开始：

- 手机端和 Web 端 MVP 已达到发行候选状态。
- API 和内容模型已稳定，不需要 TV 专用破坏性修改。
- 已取得至少一台目标电视、一台电视盒子和两类 USB 舞毯。
- 已确认 TV 端真实用户场景和最低设备范围。
- TV 工作不会中断手机/Web 的高严重度缺陷修复。

该阶段包含 Leanback 入口、遥控器焦点、USB HID 映射、设备断线、电视延迟校准、单人舞毯，以及后续双人评估。

## 6. 前两个迭代建议任务

> 2026-09-27 进度：服务端扫描、SQLite、类型化 OpenAPI v1 草案，以及 Web 选歌—Tap/Hold/Roll/Mine 游玩—结算纵向链路已有可运行初版。扫描互斥、清单 ETag、素材 Range、输入事件时间戳、基础校准与失焦安全终止已经验证。共享测试向量覆盖时间轴、持续音符与 Mine 输入序列；Docker 实机构建、判定精度测量和正式计分仍未完成，因此 M1 仍为进行中。

### 迭代 1：确定数据与时钟

| 编号 | 任务 | 完成定义 |
|---|---|---|
| BASE-001 | 建立代码仓库与模块目录 | 服务端、Web、Android、规范和测试目录清晰，基础检查可运行 |
| SPEC-001 | 定义 API v1 草案 | 清单、单曲、谱面、资源、错误和版本字段有机器可读定义 |
| SPEC-002 | 定义统一谱面模型 | 第一阶段 timing 与 note 类型均可无损表达 |
| TEST-001 | 建立最小测试歌曲集 | 覆盖固定 BPM、变速、Stop、Delay、Warp、Hold 和 Mine |
| TEST-002 | 建立判定测试向量 | 给定音频位置与输入时间，预期判定完全确定 |
| LEGAL-001 | 建立依赖与许可台账 | 核心库、测试媒体和代码来源均有许可状态 |
| SPIKE-001 | 验证 Web Audio 时钟 | 输出误差数据，明确是否存在阻断性问题 |
| SPIKE-002 | 验证 Android 音频时钟 | 在至少一台真机输出 underrun 和时钟误差数据 |

| 编号 | 任务 | 完成定义 |
|---|---|---|
| SRV-001 | Docker 服务骨架 | arm64/amd64 构建定义、健康检查和持久化目录可用 |

| WEB-003 | 最小四轨游玩 | 键盘输入、音符绘制、判定和结算形成闭环 |

## 7. 依赖关系

```text
测试歌曲与统一模型
        ├────────> 服务端解析与 API ────────> Web 纵向切片
        │                    └──────────────> Android 远程曲库
        └────────> 判定测试向量 ────────────> Web/Android 等价性

Android 音频验证 ────────> Android 纵向切片
API v1 候选 + 手机/Web RC ─> Android TV 启动评审
```

## 8. 任务与变更管理

- 每个任务必须关联 PRD 编号或标记为 `SPIKE`、`BUG`、`DEBT`。
- 当前迭代中途新增功能默认进入候选池；只有阻断缺陷、安全问题或明确替代当前任务时才能插入。
- 需求变更必须记录：用户问题、主轴关联、接受/延后/验证/拒绝结论、影响的里程碑。
- 修改 API 或谱面语义时必须同时更新测试数据和两端兼容说明。
- 对“顺便做”“以后可能用到”“加起来不难”的需求默认持怀疑态度，并要求给出可验证收益。

## 9. 决策检查点

### 检查点 A：M0 结束

决定解析逻辑放在服务端还是共享运行时，并确认 Web/Android 获取原始或预解析谱面数据的最终边界。

### 检查点 B：M1 结束

根据 Web Audio 实测决定 Web 的延迟承诺，以及是否在 MVP 中保留 Firefox 全支持。

### 检查点 C：M2 结束

根据 Android 真机数据决定最低 Android 版本、最低性能等级和游戏核心是否需要迁移至 C++。

### 检查点 D：M3 结束

冻结 API v1 候选和 MVP 谱面兼容范围；之后新增格式默认进入 M5。

### 检查点 E：M4 结束

评审是否满足 TV 启动门槛。未满足时继续修复手机/Web，不因已有 TV 设想而提前开工。

## 10. 当前已知阻塞与待决策

当前没有已确认的技术阻塞。开始编码前需要依次确认：

1. 是否建立 Git 仓库及开源许可证。
2. 第一阶段使用的无版权风险测试歌曲和谱面来源。
3. Web 渲染库在 PixiJS 与 Phaser 之间的选择。
4. 服务端谱面解析库是否满足标准 `.ssc` 语义。
5. Android 最低版本和首批真机。
6. 开发人力，以便把工作量级别换算为发布日期。
