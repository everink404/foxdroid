# FoxDroid 技术路线

> 状态：初稿  
> 版本：0.4  
> 日期：2026-09-08

## 1. 技术结论

推荐采用“内置 Web 客户端的家庭内容服务 + 可选连接的 Android 原生客户端”路线，而不是以修改 Project OutFox 官方程序为前提。

主要理由：

- Project OutFox 当前未公开完整核心源码，无法把它作为可控的直接修改基础。
- StepMania 格式、判定模型和相关开源实现足以作为兼容性参考。
- Android 手机、浏览器和电视对界面、输入、音频、生命周期及存储有独立要求；首期只实现手机和桌面 Web，电视适配延后。
- 可选内容服务只解决集中曲库管理，不应成为游戏运行时依赖。
- 服务端预扫描并生成清单，可以避免每台 Android 设备通过 SMB 枚举大量小文件。
- Web 客户端由服务端直接托管，可覆盖 Windows、macOS 和 Linux 用户，不要求现有 StepMania 分支理解新接口。

总体技术关系：

```text
                   NAS + Docker 内容服务
          ┌──────────────────────────────────┐
          │ 扫描 / 解析 / SQLite 索引        │
          │ 清单 API / 谱面 API / 资源 API   │
          │ 内置 Web 客户端静态资源          │
          └───────────────┬──────────────────┘
                          │ HTTP(S)
             ┌────────────┴─────────────┐
             │                          │
┌────────────▼────────────┐  ┌──────────▼───────────────┐
│ 浏览器 Web 客户端       │  │ Android 原生客户端       │
│ Windows/macOS/Linux     │  │ 首期：Android 手机        │
│ Web Audio/Keyboard      │  │ Oboe / Touch             │
└─────────────────────────┘  └──────────────────────────┘
       各客户端在本地完成音频时钟、输入、判定与计分

                 后续：Android TV / USB HID 跳舞毯
```

## 2. 技术选型建议

### 2.1 Android 客户端

| 领域 | 建议 | 原因 |
|---|---|---|
| 应用层 | Kotlin | Android 生命周期、设置、权限和网络支持成熟，并为后续电视适配保留基础 |
| 界面 | Jetpack Compose | 手机设置、曲库和普通页面开发效率高；TV 组件后续引入 |
| 游戏核心 | 独立纯逻辑模块；原型期 Kotlin，性能证据出现后再迁移 C++ | 降低首期 NDK 复杂度，保持判定逻辑可测试 |
| 游戏渲染 | OpenGL ES 3.0 | 覆盖首期目标手机且渲染时序可控；电视硬件降级策略后续评估 |
| 音频 | Oboe/AAudio 原生模块 | 获取低延迟输出、稳定回调和硬件时间戳 |
| 网络 | OkHttp | 局域网接口、断点与超时控制成熟 |
| 数据库 | Room / SQLite | 本地曲库、远程清单快照、成绩和缓存状态 |
| 序列化 | JSON 用于控制面；二进制文件用于媒体 | 易调试，首期复杂度低 |
| 图片 | 支持磁盘缓存的 Android 图片加载库 | 封面列表性能与缓存管理成熟 |

不建议首期直接移植整个 StepMania 5 / ITGmania C++ 引擎。该路线会同时引入桌面窗口系统、文件系统抽象、Lua 主题、旧音频驱动和大量非 MVP 模式。可以复用其格式语义、测试数据或许可证允许的独立代码，但 Android 客户端应保持边界清晰。

PadManiacs 等 Web/Cordova 项目适合作为交互和兼容性参考，但手机端低延迟音频和触控时间戳仍是核心要求，不建议把 WebView 作为 Android 正式游戏运行时。

### 2.2 内容服务端

| 领域 | 建议 | 原因 |
|---|---|---|
| 运行方式 | Docker / Docker Compose | 适合主流 NAS，部署与持久化明确 |
| 服务语言 | Python 3 + FastAPI | 可复用成熟 `.sm/.ssc` 解析库，原型与维护成本低 |
| 数据库 | SQLite | 家庭单节点读取为主，备份和重建简单 |
| 文件监控 | 周期扫描为基础，文件系统事件为加速 | NAS 挂载和不同文件系统上的事件不总是可靠 |
| API | HTTP JSON + 带 Range 支持的资源响应 | 浏览器和 Android 均支持成熟，便于调试和媒体读取 |
| 发现 | mDNS / DNS-SD，手动地址始终可用 | 提升家庭部署体验，同时保留确定性入口 |
| 日志 | 结构化日志 | 便于定位损坏谱面、路径和媒体问题 |
| Web 托管 | FastAPI 静态资源或同容器反向代理 | 单地址交付，避免额外部署步骤 |

服务端无需在首期采用 PostgreSQL、Redis、消息队列或对象存储。这些组件对单家庭 NAS 场景不会提高核心可靠性。

### 2.3 Web 客户端

| 领域 | 建议 | 原因 |
|---|---|---|
| 语言 | TypeScript | 类型化共享 API 模型，浏览器生态成熟 |
| 构建 | Vite | 构建简单，可输出由服务端直接托管的静态资源 |
| 渲染 | PixiJS 或 Phaser | WebGL/Canvas 降级、资源和输入生态成熟 |
| 音频 | Web Audio API | 可获得精确音频时间轴和预解码能力 |
| 控制器 | Keyboard Event + Gamepad API | 覆盖桌面键盘、标准手柄和部分 HID 舞毯 |
| 本地缓存 | Cache Storage + IndexedDB | 保存清单、谱面和按策略缓存媒体 |
| 安装能力 | PWA | 可选提供接近桌面应用的启动体验 |

Web 客户端可以提供完整基础玩法，但不能预先承诺与 Android 原生 Oboe 客户端相同的最低延迟。浏览器和操作系统音频后端差异较大，因此首期将 Web 端定位为桌面浏览器键盘可用、延迟可校准；Gamepad、跳舞毯和竞技级指标在后续实测后决定。

## 3. 客户端模块边界

本章中的内容源和游戏核心边界同时适用于 Android 与 Web 客户端。两端共享协议定义、谱面数据模型、判定测试向量和兼容性测试集，不强制共享同一种运行时实现。

### 3.1 内容源接口

本地曲库与远程服务实现同一抽象，避免选歌和游戏层感知 SMB、HTTP 或 Android 文件选择器。

概念接口包括：

```text
ContentSource
  - sourceId
  - availability
  - refreshCatalog()
  - listSongs(query)
  - getSong(songId)
  - prepareSong(songId, chartId)
```

建议实现：

- `LocalContentSource`：管理用户导入到应用空间的本地歌曲。
- `ServerContentSource`：同步服务器清单并按需获取资源。
- `BundledContentSource`：可选，用于合法内置的教程或校准内容。

Web 客户端只有与当前服务同源的 `ServerContentSource`；Android 原生客户端可同时注册本地、远程和内置来源。

服务端开关只决定 `ServerContentSource` 是否注册和刷新，不改变游戏引擎行为。

### 3.2 统一内容模型

客户端内部使用稳定的统一模型：

- `Source`：内容来源及可用状态。
- `Song`：标题、艺术家、分组、预览点、媒体引用。
- `Chart`：模式、难度、等级、谱师、时间数据和音符数据引用。
- `Asset`：音频、封面、背景和视频的内容标识、大小和校验值。
- `PreparedSong`：开始游戏所需资源已经满足的本地状态。

同一歌曲可能来自本地和服务端。首期以来源隔离为准，不自动合并；后续可通过内容校验值识别重复项。

### 3.3 游戏核心

游戏核心保持无网络、无数据库依赖，只接收：

- 已解析的谱面时间轴。
- 本地可读取的音频和媒体句柄。
- 输入事件及其单调时钟时间戳。
- 校准参数和玩法配置。

核心输出：

- 当前节拍、可见音符和动画状态。
- 判定结果、连击、生命和分数。
- 最终成绩和诊断数据。

这种边界保证服务端断开不会改变判定，也便于用固定输入序列做确定性测试。

## 4. 服务端扫描与数据库

### 4.1 扫描职责

服务端扫描器负责：

1. 枚举配置的曲库根目录。
2. 识别歌曲文件夹和谱面文件。
3. 读取 `.sm/.ssc` 并解析歌曲、谱面和时间信息。
4. 验证引用的音频、图片和视频是否存在。
5. 计算稳定内容标识和必要校验值。
6. 以事务方式更新数据库并生成新的曲库版本。
7. 保留单曲错误，继续处理其他内容。

### 4.2 增量判断

第一层使用相对路径、文件大小和修改时间判断是否变化；只有变化或冲突时再计算内容哈希。这样可减少大曲库在机械硬盘上的重复读取。

以下情况需要重新解析：

- 谱面文件新增或删除。
- 文件大小或修改时间变化。
- 解析器版本升级且数据结构发生变化。
- 管理员请求完整重建。

### 4.3 数据库建议结构

```text
library_state
  catalog_revision, scanner_version, last_scan_at, last_scan_status

songs
  id, relative_path, title, subtitle, artist, group_name,
  preview_start, preview_length, fingerprint, updated_at

charts
  id, song_id, step_type, difficulty, meter, credit,
  chart_fingerprint, timing_payload, note_payload

assets
  id, song_id, kind, relative_path, mime_type,
  size, content_hash, modified_at

scan_errors
  relative_path, error_code, message, observed_at
```

任何客户端都不直接打开服务端 SQLite 文件。数据库属于服务端实现细节，客户端只接收稳定 API 模型。这避免 SQLite 文件锁、SMB 随机访问和数据库结构升级泄漏到客户端。

## 5. 服务接口边界

以下为接口职责草案，不作为最终 URL 承诺：

| 接口 | 职责 |
|---|---|
| `GET /api/v1/health` | 服务健康状态 |
| `GET /api/v1/server` | 服务器名称、版本和能力 |
| `GET /api/v1/catalog` | 返回指定版本后的曲库快照或变更 |
| `GET /api/v1/songs/{songId}` | 单曲详情和谱面列表 |
| `GET /api/v1/charts/{chartId}` | 获取解析后的谱面与时间数据 |
| `GET /api/v1/assets/{assetId}` | 获取音频、图片或视频资源 |
| `GET /` | 返回与服务端版本匹配的 Web 客户端 |

接口需要满足：

- 服务器生成的稳定 ID，不使用 NAS 绝对路径作为标识。
- 返回 `catalogRevision`，客户端可以判断清单是否变化。
- 资源携带长度、MIME、ETag 或内容哈希。
- 大文件支持 HTTP Range。
- 删除项能通过增量清单传递给客户端。
- 客户端与服务端协商 API 版本和谱面数据版本。

## 6. 内容准备与缓存语义

### 6.1 清单缓存

- 服务器清单同步到客户端 Room 数据库。
- 应用启动先显示本地快照，再异步确认服务器版本。
- 服务器关闭或离线时，上次清单可继续展示，但标记为离线。

### 6.2 游玩准备

进入游戏前必须确认：

- 谱面和时间数据完整。
- 音频已达到可保证连续播放的状态。
- 必要解码器可用。
- 校验值与清单一致。

MVP 建议将所选歌曲的音频和谱面完整准备到 Android 本地缓存或 Web 客户端内存/浏览器缓存后再开始。背景视频可以按能力选择完整准备或禁用；不得让游戏判定依赖持续网络读取。

### 6.3 缓存失效

缓存以 `assetId + contentHash` 标识。服务器曲库更新时，新资源生成新的校验值；正在使用的旧缓存不得在游戏中途被删除。

## 7. 谱面兼容路线

### 7.1 第一阶段

- `.sm`。
- 标准 `.ssc`。
- `dance-single`。
- Tap、Hold、Roll、Mine。
- BPM、Offset、Stop、Delay、Warp。

### 7.2 第二阶段候选

- `dance-double` 和本地双人。
- Pump 五键模式。
- Fake、Scroll、Speed 等更复杂段落的兼容性补全。
- DWI 和其他 OutFox 支持格式。

### 7.3 兼容性测试

建立不包含未授权媒体的测试谱面集，每个文件聚焦一种语义：

- 固定 BPM。
- 多次 BPM 变化。
- 正负 Offset。
- Stop / Delay / Warp 边界。
- 不同分辨率音符。
- Hold / Roll 起止重叠。
- 损坏字段和缺失媒体。

服务端解析结果与客户端判定使用同一版本化数据定义，避免双方各自解释谱面造成差异。

## 8. 音频与判定路线

### 8.1 时钟

- 使用单调时钟记录输入事件。
- 使用音频硬件帧位置或 AAudio/Oboe 时间戳估算实际播放位置。
- 渲染帧只负责显示，不作为判定时间来源。
- 网络时间、服务器时间和系统墙上时钟不得进入判定计算。

### 8.2 音频线程

- 使用 Oboe 请求低延迟性能模式。
- 优先使用设备原生采样率，通常为 48 kHz。
- 使用音频回调供给数据，禁止在回调中读取网络或查询数据库。
- 记录 buffer underrun，作为设备兼容性指标。

### 8.3 校准模型

至少分离：

- 音频输出偏移。
- 视觉显示偏移。
- 输入设备偏移。

设置按 Android 设备和输入设备保存。首期对蓝牙音频显示高延迟警告；电视游戏模式提示在 TV 阶段加入。

## 9. 输入路线

### 9.1 手机触控

- 使用原始触控事件的事件时间，而不是事件处理完成时间。
- 维护每个 pointer 与轨道的归属。
- 正确处理 `DOWN`、`POINTER_DOWN`、`MOVE`、`POINTER_UP`、`UP` 和 `CANCEL`。
- 触控采样、判定和绘制解耦。

### 9.2 Android TV 与跳舞毯（MVP 后）

- 同时处理 `KeyEvent` 和游戏手柄 `MotionEvent`。
- 根据 Android 输入设备描述、Vendor ID、Product ID 和 descriptor 保存映射。
- 不假定方向一定表现为方向键；某些转接器会表现为摇杆轴。
- 映射过程支持检测同时按键、长按和轴阈值。
- 断开时暂停，重连同一设备后恢复玩家归属。

### 9.3 Web 输入

- 键盘事件使用浏览器提供的高精度事件时间戳，并屏蔽会触发页面滚动的游戏按键默认行为。
- MVP 使用键盘输入；Gamepad API 和 USB 跳舞毯兼容性在后续阶段验证。
- 后续 Gamepad API 在渲染循环中读取并记录采样时刻，不假设所有 USB 舞毯都会暴露为标准手柄。
- 表现为键盘的 USB 舞毯按键可能被浏览器或操作系统保留，需要能力诊断和按键映射。
- 页面失去焦点、可见性改变或控制器断开时立即暂停。
- Web 端校准数据按浏览器、输出设备和控制器配置保存在本地。

## 10. Android 平台要求

### 10.1 手机优先与电视扩展

首期 App Bundle 只承诺 Android 手机体验：

- 手机入口使用触控导航和横屏游戏界面。
- 不把 Leanback、遥控器焦点导航或电视商店审核作为 MVP 退出条件。

进入 TV 阶段后，再评估同一 App Bundle 增加 Leanback 入口，或拆分电视产品变体；两者都应共享谱面、判定、网络和资源模块。

### 10.2 局域网权限

- 服务端功能关闭时不触发局域网访问。
- Android 17 / API 37 起，启用服务器连接前请求 `ACCESS_LOCAL_NETWORK`。
- 权限拒绝后保留本地模式，并在设置页显示原因和再次授权入口。

### 10.3 生命周期

- 失去音频焦点时暂停。
- Activity 停止时释放或挂起音频流。
- 恢复时重新建立音频时钟，不沿用失效时间基准。
- TV 阶段增加环境模式和电视生命周期处理。

## 11. Docker 部署边界

概念挂载：

```text
/library   只读歌曲目录
/data      SQLite、索引状态和持久化配置
/config    可选静态配置
```

容器要求：

- 非 root 用户运行。
- `/library` 默认只读。
- 支持 `linux/amd64` 和 `linux/arm64`。
- 提供健康检查。
- 优雅结束正在进行的扫描并保持最后一个完整数据库版本。
- 数据库升级前自动备份或可以无损重建。

NAS 已经提供 SMB 时，容器直接挂载 NAS 本地曲库目录，不需要在容器内再次通过 SMB 访问自身。Android 与 Web 客户端都不需要任何 SMB 库。

## 12. 安全路线

### 12.1 初始家庭局域网模式

- 默认绑定到明确配置的网络接口或所有局域网接口。
- 可选访问令牌。
- 资源标识映射到服务端验证后的记录，禁止接受任意文件路径。
- 对清单、谱面和资源接口实施大小、范围和速率限制。
- 日志隐藏认证信息。

### 12.2 非目标边界

初始版本不应直接暴露到公网。若未来支持远程家庭访问，需要另行评估 TLS、身份认证、反向代理、限流、账户和版权风险，不能把局域网模式直接视为公网安全。

## 13. 测试路线

### 13.1 自动化测试

- 谱面解析黄金文件测试。
- 时间轴 beat 与秒数双向转换测试。
- 固定输入序列的确定性判定测试。
- 清单全量与增量同步测试。
- 缓存命中、失效和中断恢复测试。
- 路径穿越、超大文件和损坏媒体测试。

### 13.2 设备测试矩阵

MVP 至少覆盖：

- 一台中端 60 Hz 手机。
- 一台高刷新率手机。
- Windows、macOS 和 Linux 各至少一个当前版桌面浏览器环境。
- 常见桌面键盘同时按键场景。
- Wi-Fi 与有线网络。
- x86_64 与 arm64 NAS 至少各一次容器构建验证。

TV 阶段追加：

- 一台 Google TV / Android TV 电视。
- 一台主流 Android 电视盒子。
- 键盘型 USB 舞毯。
- 游戏手柄型 USB 舞毯或 PS2 转 USB 适配器。

### 13.3 延迟测试

- 记录输入事件时间、判定时间、音频帧位置和渲染帧时间。
- 使用高速摄像或外部音频回环验证端到端偏移。
- MVP 分别测试手机内置扬声器、有线音频和蓝牙音频，并覆盖桌面浏览器常见输出。
- TV 阶段再测试电视游戏模式、HDMI 音频和电视外接音响。

## 14. 阶段路线

### 阶段 A：风险验证

- `.sm/.ssc` 解析一致性。
- 一首歌的本地音频时钟、绘制和判定。
- 手机多点触控。
- Docker 扫描一份真实规模曲库并生成清单。
- 客户端通过接口准备并完成一局远程来源歌曲。
- 桌面浏览器通过服务根地址完成选歌、键盘输入、音频播放和一局游戏。

退出条件：没有影响产品成立的音频、输入、曲库或设备兼容性障碍。

### 阶段 B：MVP

- 完成本地曲库和设置页。
- 完成可选服务器开关、清单同步和资源缓存。
- 完成选歌、游玩、结算和校准。
- 完成目标设备稳定性测试。
- 完成服务端内置 Web 客户端的桌面浏览器兼容性测试。

### 阶段 C：兼容与体验完善

- 扩充谱面语义和媒体格式。
- 自动发现、诊断和缓存管理。
- 根据真实数据优化加载、延迟和耗电。
- Web Gamepad API 与桌面 USB 舞毯兼容性验证。

### 阶段 D：发行准备

- Android 手机应用商店合规、隐私说明和 Web 发布检查。
- Docker 镜像发布、升级和回滚验证。
- 内容许可审计和用户文档。

### 阶段 E：Android TV 与跳舞毯

- 增加 Android TV / Google TV 入口和遥控器焦点导航。
- 验证 USB HID 键盘型、手柄型跳舞毯及转接器。
- 增加按设备映射、断线恢复和电视延迟校准。
- 评估单 APK 与独立电视变体，并完成电视应用商店质量检查。
- 在单人稳定后再评估双舞毯和本地双人。

## 15. 主要技术风险

| 风险 | 严重度 | 判断 |
|---|---:|---|
| Android 设备音频延迟差异 | 高 | 可校准，但必须尽早真机验证 |
| 跳舞毯键值、轴和多键能力差异 | 高 | TV 阶段验证；可通过映射缓解，劣质硬件无法由软件完全修复 |
| `.ssc` 方言和高级特性差异 | 中高 | 通过明确兼容范围和测试集控制 |
| 大型曲库扫描耗时 | 中 | 服务端增量索引可有效控制 |
| Wi-Fi 中断影响媒体 | 中 | 游玩前准备与本地判定边界可控制 |
| 电视性能和解码能力碎片化 | 中 | 延后至 TV 阶段，不作为手机/Web MVP 阻塞项 |
| 浏览器音频与 Gamepad 输入延迟差异 | 高 | Web 端单独校准，竞技级目标等待实测 |
| 电视内置浏览器能力不足 | 高 | 不纳入 MVP 支持范围；TV 阶段使用 Android 原生端 |
| OutFox 完整兼容预期 | 高 | 产品命名和范围必须明确，不承诺完整引擎兼容 |
| 音乐、主题和编解码器许可 | 高 | 需要独立审计，不能由技术兼容性替代 |

## 16. 需要验证后再决定的选项

1. 游戏核心长期使用 Kotlin，还是将判定和谱面模型迁移至共享 C++。
2. Compose 与 OpenGL 游戏画面的具体组合方式。
3. 服务器返回原始谱面，还是返回版本化的预解析谱面数据；MVP 倾向后者，同时保留原始文件下载能力。
4. 音频必须完整缓存后开始，还是允许达到安全缓冲阈值后开始。
5. 是否首版支持自动发现；手动地址必须始终保留。
6. 本地与远程重复歌曲的展示和合并规则。
7. 开源许可证与第三方代码复用范围。
8. Web 客户端首期的浏览器支持矩阵和延迟等级承诺。
9. 是否让 Web 客户端同时承载管理员扫描状态、日志和配置页面。
