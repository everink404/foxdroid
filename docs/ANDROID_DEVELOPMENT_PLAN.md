# FoxDroid Android 手机端开发规划

> 制定：2026-10-04
> 状态：A0/A1 已实现，A2 已有可游玩原型，A3 正在推进；完整验收见项目状态
> 范围：Android 手机；对应总规划 M0、M2、M3、M4

## 1. 目标与边界

首个交付目标是：全新安装后，不配置 NAS，也能导入一份本地 `.sm`/`.ssc` 曲包，选择 `dance-single` 谱面，在横屏用四轨触控完成一局并看到本地成绩。第二个目标是在设置中主动开启内容服务器，连接现有 FoxDroid 地址、同步曲库并游玩远程歌曲。游玩开始后，网络不得进入音频时钟、输入或判定链路。

首期只做手机触控。Android TV、舞蹈毯、双人、公网账户和完整 OutFox 主题兼容不进入本规划。浏览器端的独立校准页、按键反馈和 UI 参考方向仍在[优化想法](./OPTIMIZATION_IDEAS.md)中，不作为 Android 开发前置任务。

## 2. 当前起点与需要补齐的契约

- 已有服务端与 Web 纵向链路、`shared/api/openapi-v1.json` 草案、`shared/test-vectors/` 以及原创 `.sm/.ssc` 黄金曲库。
- 当前仓库已有 Android 工程、本地导入、音频与游玩原型。服务端解析器为 Python，本地模式使用 Kotlin 实现及共享测试向量。
- 现有 API 提供服务器信息、完整曲库清单、歌曲详情、解析后的谱面和媒体资源。清单有 `catalogRevision` 与条件缓存；当前模型没有资源内容哈希或增量删除列表。Android 首版采用完整清单快照替换，并在同步时识别新增、修改和删除；文件级增量协议留待 M3。
- Android 的本地内容和远程内容使用统一选歌模型，但保留来源身份；同名歌曲不自动合并。

## 3. 推荐结构

| 部分 | 职责 | 首期实现原则 |
|---|---|---|
| `app` | 导入、曲库、选歌、设置、结算页面与导航 | Kotlin；普通页面可用 Compose，游戏画面独立渲染 |
| `content-model` | Song、Chart、Asset、PreparedSong 和来源状态 | 不依赖 Android UI 或网络 |
| `content-local` | 文件选择、ZIP 导入、解析、索引和本地资源 | 导入后保存在应用管理空间；单曲失败不阻塞曲库 |
| `content-server` | API 客户端、清单快照、资源下载和缓存 | 开关默认关闭；只有开启后才访问局域网 |
| `game-core` | 时间轴、输入状态、判定、连击和分数 | 纯逻辑 Kotlin；以共享向量做确定性测试 |
| `game-runtime` | 音频时钟、触控事件、渲染、生命周期 | Oboe/AAudio 音频模块与游戏核心之间保持清晰接口 |
| `storage` | 本地曲库索引、远程快照、成绩与设置 | Room/SQLite；扫描和数据库操作不在游戏实时线程 |

本地导入可通过系统文件选择器选目录或 ZIP。目录访问使用 Storage Access Framework；导入时复制所需文件到应用管理空间，避免游戏运行中依赖外部文档提供者。ZIP 导入需要校验路径、文件数量与总解压大小，并能报告损坏或不支持的内容。[Android 文件访问说明](https://developer.android.com/training/data-storage/shared/documents-files)

## 4. 实施顺序与完成定义

### A0：工程骨架与可运行诊断版

1. 建立 Android Gradle 工程、`arm64-v8a` 构建和持续集成检查；先用真机启动空曲库页面。
2. 固定 `content-model` 与现有 OpenAPI 草案的字段映射，明确来源 ID、歌曲 ID、缓存键、错误展示方式和数据库迁移规则。
3. 建立诊断页或开发日志：设备型号、系统版本、屏幕刷新率、音频输出方式、音频 underrun、输入与音频时间戳；敏感地址和凭据不写入日志。
4. 选定至少一台 60 Hz 和一台高刷新率手机，记录首批可用测试曲包；最低 Android 版本暂按 PRD 的 Android 10 建议，真机验证后决定。

**完成定义：**两台目标机能安装、启动、进入本地曲库；CI 能构建并运行纯逻辑测试；共享测试向量可被 Kotlin 测试读取。

### A1：离线曲库与谱面准备

1. 导入文件夹与 ZIP；识别 `.sm`、标准 `.ssc`，优先处理 `dance-single`，显示歌曲、难度、等级、音乐与封面。
2. 本地解析和时间轴通过共享黄金曲库及测试向量；完成损坏谱面、缺失音频、重复导入、内容变更与删除的处理。
3. 建立统一的 `ContentSource` 接口、本地索引和选歌页；曲目准备阶段验证谱面和音频可读，失败时留在选歌页并显示原因。
4. 首轮只用原创测试曲包和合法音频打通“导入—选歌—准备”，并把准备好的内容交给游戏运行层。

**完成定义：**全新安装、服务器功能关闭、飞行模式下可导入并看到曲包；坏歌不阻塞好歌；至少一首四轨歌曲的谱面和音频能完整准备供 A2 游玩。

### A2：音频、触控与判定

1. 先做真机音频实验：请求低延迟输出，使用 Oboe 回调与硬件时间戳估算播放位置；记录采样率、缓冲与 underrun。音频回调内不做文件、数据库或网络 I/O。[Android 低延迟音频建议](https://developer.android.com/games/sdk/oboe/low-latency-audio)
2. 触控按原始事件时间戳记录；维护 pointer 与四轨的归属，覆盖同时按下、移动、抬起和取消；渲染帧时间不得替代输入或音频时钟。
3. 接入 Tap、Jump、Hold、Roll、Mine 和 BPM、Offset、Stop、Delay、Warp；判定、计分、连击与结算由同一套纯逻辑状态机驱动。
4. 实现音频与视觉基础偏移设置、本地保存和可恢复的暂停；输入偏移可先保留模型与手动设置入口，具体设备级校准在真机数据后细化。

**完成定义：**两台目标机各完成至少两局带音频游玩；四点同时触控、长按和抬起正确；同一谱面和固定输入序列的 Kotlin 判定结果与共享向量一致；记录实际音画偏差及 underrun。

### A3：可选家庭内容服务器

1. 设置页开关默认关闭。开启后允许手动输入地址并测试 `/api/v1/server`；显示服务名称、版本、曲数和连接错误。未开启时不发起服务连接。
2. 使用当前完整清单 API 同步到本地快照，选歌页同时显示本地与远程来源；服务离线时先展示已同步快照，并标明不可获取的资源。
3. 获取歌曲详情、谱面和音频；在开始游戏前下载并验证本局必需资源。下载失败可重试，不能进入缺资源的游戏。开始后断网，本局仍可完成。
4. 处理地址错误、超时、清单变化、歌曲删除、资源缓存过期和服务关闭；成绩始终保存在客户端本地。
5. 测试 Android 17 / 目标 SDK 37 及以上的局域网权限流程：只在启用服务功能且需要访问局域网时请求，拒绝后本地模式照常可用。较低目标 SDK 不提前声明此权限。[Android 局域网权限说明](https://developer.android.com/privacy-and-security/local-network-permission)

**完成定义：**连接现有 NAS 服务后能同步真实曲包并完成一局；关闭服务功能、NAS 关机或断网均不阻塞本地选歌和游玩；远程歌曲准备好后断网不影响本局判定。

### A4：M2 验收与 M3/M4 交接

1. 验证来电或其他应用抢占音频、锁屏、切后台、旋转及 Activity 重建；失去音频焦点时暂停，恢复时重新建立时钟，不能沿用旧时间基准。[Android 音频焦点说明](https://developer.android.com/media/optimize/audio-focus)
2. 用真实 `.sm/.ssc` 曲包复核支持范围与异常；服务端和 Android 对相同谱面/输入序列运行共享向量。差异形成缺陷清单，不靠主观手感代替判定测试。
3. 记录包体、启动时间、导入与同步耗时、60 FPS 稳定性、内存与 underrun；检查崩溃、权限拒绝、存储不足、坏 ZIP、坏谱面和缓存清理。
4. M3 再补文件级增量同步、正式规则等价性与 API `v1` 候选；M4 再做发行级安全、备份、升级与隐私检查。

**M2 退出条件：**A1+A2 离线闭环和 A3 可选服务闭环均通过；60 Hz 与高刷新率真机留有测试记录；四点触控、断网、后台与音频焦点场景通过；没有阻塞主流程的高严重度缺陷。

## 5. 建议的首批工作项

| 顺序 | 工作项 | 可交付结果 |
|---:|---|---|
| 1 | Android 工程与目标机确认 | 可安装的空壳 APK、两台测试机信息、CI 构建 |
| 2 | Kotlin 读取共享契约与向量 | API 字段模型和时间轴/判定测试可运行 |
| 3 | 本地目录导入与最小解析 | 原创曲包进入曲库；坏歌有单独错误 |
| 4 | 真机音频与四点触控实验 | 采样率、时间戳、underrun 与触控记录 |
| 5 | 本地完整一局 | 带音频结算、本地成绩、飞行模式复测 |
| 6 | 服务开关与完整清单同步 | NAS 真曲包选歌、资源准备与断网复测 |

上述顺序以风险和可验收结果为依据。A1、A2 可短时间交叉推进，但在 A1 本地闭环完成前，不把远程服务连接当作主入口。

## 6. 待确认事项与记录要求

### MVP 后优化：音频格式兼容

用户确认 NAS 曲库能够识别，但部分歌曲提示音频格式不支持。另立兼容性工作项：收集失败音频的扩展名、容器、编码和服务端 MIME，核对本地与远程来源的格式限制，补全 MIME 别名及实际可解码格式判断，完善错误分类。使用原创/合法素材验证本地与 NAS 两条链路的准备及完整游玩，防止已支持格式回退。具体失败格式尚待采集，本项尚未实现；详见 [优化记录](./OPTIMIZATION_IDEAS.md)。

### MVP 后优化：音频准备耗时

用户已确认修复版能正常解码和游玩，并明确先完成最小 MVP。预解码过慢保留为性能问题，移至 MVP 之后，不阻塞 A2/A3。届时测量各阶段耗时，优化重复转换/写盘和全量等待，评估短前导缓冲启动及缓存复用；音频回调继续禁止解码、文件 I/O 和阻塞。暂定目标：两台目标机上的两三分钟 WAV/MP3/OGG 首次准备 ≤5 秒、重复准备 ≤1 秒，每种至少三次，记录最差值、内存、缓存占用和完整游玩的缺帧/underrun。该目标尚未达成。详见 [优化记录](./OPTIMIZATION_IDEAS.md)。

- 首批 60 Hz 与高刷新率 Android 真机型号、系统版本、音频输出方式；这些决定音频实验和最低版本决策。
- 本地导入首先支持“选目录”和“选 ZIP”两种入口；若设备文件提供者兼容性不佳，保留复制导入作为可靠路径。
- 当前服务端 API 缺少资源内容哈希和增量删除协议。A3 使用完整快照；进入 M3 前先明确缓存键、协议变更及迁移方案。
- 每项真机验收记录设备、Android 版本、应用构建、测试曲包、步骤、结果和失败日志；用户真实曲包不提交到公开仓库。
