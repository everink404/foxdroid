# FoxDroid 项目状态与后续规划

> 状态：执行中  
> 快照日期：2026-10-04
> 当前阶段：M1 服务端与 Web 纵向切片  
> 性质：可运行原型，尚未达到 MVP 或发行候选标准

## 1. 一页结论

FoxDroid 的技术方向已经从可行性讨论进入实际开发。当前已打通以下纵向链路：

```text
本地/NAS 曲库目录
    → 服务端扫描 .sm/.ssc
    → SQLite 内容索引
    → HTTP 清单、谱面与资源接口
    → 内置 Web 选歌
    → 浏览器本地时间轴、键盘判定与结算
```

这条链路证明“可选家庭内容服务 + 内置 Web 客户端 + 后续原生客户端接入”的总体架构成立。服务器只处理内容，客户端本地完成时钟、输入和判定，网络没有进入实时判定路径。

目前不能将项目称为 MVP，主要原因是：Android 手机端尚未开始；Web 判定精度测量、正式计分和带音频人工验收证据仍需补齐；真实规模曲库与增量扫描尚未验证。用户已在实际部署环境完成真实曲包整局、Chrome 判定、断网、容器重启及兼容性现场验收，具体环境与结果待补记，详见[验收清单](./ACCEPTANCE_CHECKLIST.md)。

## 2. 已确认的产品决策

| 决策 | 当前结论 |
|---|---|
| 首要客户端 | Android 手机端与桌面 Web 端 |
| TV 与跳舞毯 | 延后到手机/Web 达到发行候选后 |
| 内容服务 | 可选功能；未来在 Android 设置页默认关闭 |
| 服务部署 | 家庭 NAS 上的 Docker/Compose 单体服务 |
| 曲库存储 | NAS/本地目录保存原始文件，SQLite 只保存服务端索引 |
| 客户端访问 | 客户端只消费清单、谱面和资源接口，不执行 SMB 扫描 |
| Web 交付 | 内容服务根地址直接提供匹配版本的 Web 客户端 |
| 实时职责 | 音频时钟、输入、判定和计分全部由客户端本地执行 |
| OutFox 关系 | 兼容 StepMania 格式语义，不承诺移植或修改闭源 OutFox 核心 |
| 项目知识管理 | 当前 Markdown 文档足够，不需要部署 Obsidian 服务 |

## 3. 当前已实现

### 3.1 内容服务

- Python 3.12、FastAPI、SQLite 服务骨架。
- `.sm` 与标准 `.ssc` 的歌曲元数据、谱面和时间标签解析。
- 递归扫描曲库；同目录优先选择 `.ssc`；损坏歌曲单独记录错误。
- 歌曲、谱面和素材稳定 ID。
- 事务式索引替换；曲库内容未变化时不增加 `catalogRevision`。
- 扫描互斥、扫描状态、开始时间、耗时和错误数量。
- 旧 SQLite 数据库字段自动迁移。
- 只读曲库设计；缺失曲库不会被服务端擅自创建。
- 路径越界检查，资源只能来自配置的曲库根目录。
- Dockerfile 与 Docker Compose 定义；容器按非 root 用户运行，曲库只读挂载。

### 3.2 HTTP API

- `GET /api/v1/health`
- `GET /api/v1/server`
- `POST /api/v1/admin/scan`
- `GET /api/v1/admin/scan-errors`
- `GET /api/v1/catalog`
- `GET /api/v1/songs/{songId}`
- `GET /api/v1/charts/{chartId}`
- `GET /api/v1/assets/{assetId}`
- OpenAPI 交互文档 `/docs`。
- 清单 ETag 与 `If-None-Match` 条件请求。
- 媒体 ETag、HTTP Range 和 `206 Partial Content`。

### 3.3 Web 客户端

- 与服务端同源交付，无需第二套部署。
- 曲库展示、搜索、重新扫描、选歌和谱面选择。
- 开始前完整取得谱面；存在音乐素材时在开始前解码到浏览器。
- Web Audio 单调时钟。
- Canvas 四轨显示与 `D F J K` 键盘输入。
- 键盘判定使用 `KeyboardEvent.timeStamp` 还原事件实际发生时间，避免主线程排队时间进入判定误差。
- 判定偏移与视觉偏移可独立调整（±250 ms）并保存在浏览器本地；视觉偏移不污染实际判定时钟。
- Perfect、Great、Good、Miss、分数、连击、准确率和结算页原型。
- 页面失焦或音频时钟中断时安全终止本局，不沿用失效时间基准。
- 当前支持 Tap Note、Jump，以及 BPM、Offset、Stop、Delay、Warp 时间轴。
- Warp 区间不消耗时间；Warp 内普通音符被剔除；同拍 Stop/Delay 例外已覆盖。
- Hold、Roll、Mine 已有语言无关解析模型、可配置判定规则和共享输入序列，并已接入实时 Web 显示、按下/松开状态与结算。

### 3.4 自动验证

当前自动化结果：

- 9 项 Python 测试通过：解析器、黄金曲库扫描与错误隔离、数据库幂等、HTTP 主链路、缓存、Range、测试音频确定性及 API 快照。
- 23 项 JavaScript 测试通过：时间轴、音符转换、判定边界、输入时间戳、校准值，以及共享 Tap/Hold/Roll/Mine 解析和输入序列。
- Python 静态检查与 JavaScript 语法检查通过。
- 已在内置 Chromium 浏览器走通“选歌—开局—键盘判定—结算”。
- 已在实际浏览器用包含 Hold、Roll、Mine 的测试谱面完成两局并进入扩展结算页；此项只验证运行链路，不替代人工节奏精度验收。
- 内置谱面已关联自动合成的 5 秒 WAV 节拍音频；接口已验证 `audio/wav` 与 Range 请求，仍需浏览器人工完成整局音画验收。
- 已建立首批原创、无媒体的 `.sm/.ssc` 黄金曲库，覆盖格式优先级、谱面级时间标签覆盖、缺失标题和缺失音乐；共享音符向量增加正 Offset、变速、Stop、Delay 和 Warp 暂停例外。
- 项目已初始化 Git 并发布到公开 GitHub 仓库；持续集成仍待建立。

## 4. 尚未完成与已知技术债

### 4.1 会阻止 MVP 的缺口

- Android 手机客户端尚未建立工程。
- 已有判定与视觉偏移设置，但尚无引导式自动校准，也未在多种音频/输入设备上建立推荐值。
- Hold、Roll、Mine 已接入实时游玩，但身体判定和 Mine 分值仍属于 FoxDroid 原型规则，尚未冻结为兼容计分规范。
- 当前分数模型是原型，不是承诺兼容某个 StepMania 计分版本的正式模型。
- Web 没有持久离线缓存、成绩保存或设置存储。
- Chrome、Edge、Firefox 的正式兼容矩阵尚未执行。

### 4.2 服务端缺口

- 当前每次扫描仍会遍历完整曲库；数据库只避免无变化时重写，还不是真正的文件级增量扫描。
- 未用真实大型曲库评估扫描耗时、内存和 NAS I/O。
- Docker 配置存在，但当前开发机没有 Docker，尚未完成实际镜像构建和 amd64/arm64 验证。
- 管理扫描接口没有访问令牌，只适合受信任家庭局域网，不应暴露到公网。
- 尚无结构化日志、扫描历史、自动周期扫描或文件监控。
- 字符编码目前主要覆盖 UTF-8 与 CP1252；Shift-JIS 等历史曲包需要专门样例验证。
- 已生成类型化 OpenAPI v1 草案快照，但在 Android 首次接入并反馈前不视为最终冻结。

### 4.3 项目基础欠账

- Android 工程尚未建立；共享协议/测试向量目录已建立，但覆盖面仍不足，因此 M0 不能正式验收。
- 已有首批原创黄金曲库和共享时间轴向量，但带音频测试曲仍只有一个自制谱面，未覆盖全部第一阶段语义。
- 第三方依赖和测试素材许可台账尚未完成。
- Git 仓库与公开远端已建立，持续集成尚未配置。

## 6. 推荐开发顺序

### 阶段一：补齐 M0 并关闭 M1

目标：把“可运行原型”变为可重复验收的服务端—Web 最小产品链路。

1. 扩充无版权风险的黄金测试集：首批 `.sm/.ssc` 文件已覆盖固定 BPM、变速、正负 Offset、Stop、Delay、Warp、损坏文件和缺失素材；Hold、Roll、Mine 已有共享逻辑向量，仍需补齐对应的实际曲包与音频验收样例。
2. ~~将 Web 输入判定改为使用 `KeyboardEvent.timeStamp`，并建立事件排队延迟测试。~~ 已完成。
3. 加入合法生成的测试音频（生成与接口验证已完成），继续验证浏览器实际播放位置、Offset 和断网后完成一局。
4. ~~完成 Web 判定/视觉基础校准，并将设置保存到浏览器本地。~~ 基础设置已完成；引导式自动校准后续处理。
5. ~~固化 OpenAPI/JSON 模型，形成 Android 可消费的 `v1` 草案快照。~~ 已完成；统一错误结构仍待处理。
6. 建立依赖与测试素材许可台账。
7. 在可用 Docker 环境构建镜像，验证持久化、只读曲库、健康检查和重建。
8. 完成 Chrome、Edge、Firefox 基础验证。

退出条件：从空数据目录启动服务、扫描测试曲库、浏览器选择带音频歌曲并完成一局可以稳定重复；服务在歌曲准备完成后断开不影响本局判定。

### 阶段二：M2 Android 手机纵向切片

目标：尽快验证最关键、风险最高的手机音频与触控，不等待 Web 全部美化。

1. 建立 Kotlin Android 工程和模块边界。
2. 实现本地歌曲导入、索引和四轨触控最小链路。
3. 接入 Oboe/AAudio 时钟，记录 underrun 和设备时间戳。
4. 建立设置页；内容服务开关默认关闭。
5. 实现手动服务器地址、连接测试、清单同步和资源缓存。
6. 实现音频、视觉、触控三类校准。
7. 在一台 60 Hz 和一台高刷新率手机完成真实设备验证。

退出条件：本地模式独立可玩；开启服务器后可以同步并游玩远程歌曲；服务器离线不阻塞本地模式；网络断开不影响已准备歌曲。

### 阶段三：M3 兼容与双端收敛

1. 在现有 Hold、Roll、Mine 最小链路上补齐正式规则、计分与边界样例。
2. 把时间轴和判定测试向量整理成语言无关数据，由 Web 与 Android 分别运行。
3. 为同一谱面和输入序列建立双端等价性门槛。
4. 实现服务端文件级增量扫描、删除传播和解析器版本迁移。
5. 用真实规模曲库完成扫描、同步、缓存失效与损坏隔离测试。
6. 冻结 API 和内容模型为 `v1` 候选。

### 阶段四：M4 稳定与发行候选

- 性能、内存、掉帧、音频 underrun 和缓存容量优化。
- 服务端路径、异常输入、令牌和局域网安全加固。
- Android 权限、生命周期、离线和错误恢复。
- Docker 备份、升级、重建和多架构发布验证。
- 用户文档、隐私说明和发布检查。

## 8. 需求准入规则

新需求进入当前迭代前必须同时回答：

1. 它解决哪一个手机、Web 或内容服务的具体用户问题？
2. 缺少它是否阻塞当前里程碑的退出标准？
3. 是否能复用到两个客户端或建立共享基础？
4. 是否会污染本地判定、增加新平台或带来长期兼容负担？
5. 是否有明确测试与完成定义？

结论仍只有四种：现在接受、排入后续、限时验证、明确拒绝。只有实现想法、没有用户问题或验收标准的需求，默认不进入当前迭代。
